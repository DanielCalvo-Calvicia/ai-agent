## Goal

Improve the prompts that T-06.1 lists, without breaking the answer format, with a comparison for each (Q07-4: "the prompts also need refinements").

## Files

| Action | Path |
|---|---|
| Modify | `prompts/<id>_<name>.txt` of the steps in T-06.1 |
| Create | `prompts/profiles/<profile>/<step>.txt` where only one profile differs (a file named by `prompt_replace` or `prompt_append`) |
| Modify | `docs/rules/schemas-and-prompts.md` (what the prompt of each step says and why) |

## Specification

For **each** prompt, in this order:

1. Run the fixed set on the current prompt with the models of the profile; keep the output (`before`).
2. Change **one** thing (the instruction that T-06.1 names as wrong).
3. Run the same set again (`after`); keep it.
4. Write in *Notes* what changed, the messages whose answer changed and whether the expected points are met better, the same or worse. Worse: revert.
5. The golden file changes: read the diff first and regenerate on purpose (`UPDATE_GOLDEN=1`).

A prompt that differs for one profile is a profile override (T-05.14), not a change of the generic prompt.

## Acceptance criteria

Each refined prompt has a `before` and an `after` run and a note; none breaks its schema (`test_schema_tree.py`, `assemble()`); the maintainer read each changed prompt.

## Verification

The baseline of the [tasks README](../README.md) section 3. Real runs cost money: ask before each.

## Notes

### Prompt review, read-only (2026-11-04, assistant; nothing was changed or run)

The maintainer's brief (T-06.1): no prompt is wrong; find what can be **better and use fewer tokens** (also: shorter replies, the user's language, fewer calls, fewer wrong greetings, cheaper). Sizes are bytes of `prompts/*.txt` (about 4 bytes per token; real token counts are not measured: the `before` run of the fixed set measures them). `PhaseRunner` puts the generic rules, `capabilities.txt` and the date in front of **every** call (`prompt_overrides.py`), so those two files are paid by every call of every profile.

Savings that are **not** a prompt change (they change a flow or a step, so they need the maintainer's word before T-06.5 and may reopen T-06.3):
- `data_engineer` re-emits the whole tool answer (up to 500 rows) as output tokens, one call per tool action. The Dynamics service already returns a clean table, so a code check that skips the call when the answer is already clean would save the most output tokens of the `special` flow. The T-05.11 run (8 calls, 41,513 tokens) is the baseline to measure it against.
- `draft_writer` and `editor_in_chief` are two calls for a short spoken reply; for `chat` a one-call flow would halve its calls. Not proposed to build: it changes the flow of `chat`.

Order proposed for the changes: 5 (language, lowest risk), 3, 2, 4, 6, then 1 last (it affects everything, so it is compared across all profiles once the others are settled). Every change waits for T-06.2 (the fixed set) and for the maintainer's go before any real run.
