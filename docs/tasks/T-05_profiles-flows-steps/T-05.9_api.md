## Specification

- Request fields: `profile`, `token`, `inputs`, `return` (`"text"` or `"full"`), `pause_id`, `client`. Answer fields: `profile`, `output`, `pause_id`, `discarded_pause`. A request with none gets today's answer and the `default` profile, no token.
- Errors (`error_code`): `INVALID_PROFILE` (unknown profile **and** wrong token, one generic message, 401/403; the real reason only in the log), `PROFILE_MISMATCH`, `PAUSE_NOT_FOUND`, `MISSING_INPUT` (before any model call). `SESSION_NOT_FOUND` as today. Profiles are never listed.
- `output` is the `Response` of the last step **without** `tokens_usage` and `raw`; those two are ignored in `inputs`. `inputs` is validated with the same schemas as an LLM answer and is data, never instructions.
- `pause_id` rules: the four rows of PR-005 section 6; one paused run per session; lost on restart.
- The token and `inputs` never appear in a log, a metric or a span; `client` may.
- `/session/start` takes no profile. `GET /available` is unchanged.
- `docs/api/api.md` writes the table of the steps of every profile (the client's knowledge, Q09 review) and the suggested chain `identification` -> `chat` or `movement`.

## Acceptance criteria

One test for each row of the `pause_id` table, each error code, `return` in both values, a request with no new field (today's answer), and a check that no log line holds the token (capture the log of a request with a token).
