## Goal

A flow is a JSON file; the Python flows and the registry go (PR-005 sections 3.3 and 11, S3). **No behaviour change**: the golden file is byte-identical to the one T-05.10 produced.

## Files

| Action | Path |
|---|---|
| Create | `flows/identification.json`, `chat.json`, `special.json`, `movement.json`, `gesture.json` |
| Create | `application/steps/conditions.py` (the fixed list of named conditions: `needs_user_input`, `retry_on_status`, `has_reply`, ...), `application/steps/hooks.py` (`user_clarification`, `answer_checker`, the result builders), `application/steps/action_executor.py` (the composite step) |
| Modify | `application/engine/pipeline.py` (runs the steps of a flow built from JSON: `pause_if`, `retry_on_status`, `on_pause`, `on_resume`, `result_from`) |
| Delete | `application/flows/**` (the Python flows, `registry.py`) |
| Modify | `application/engine/assemble.py` (checks the flow files: names, conditions, hooks, `result_from`) |

## Specification

- The conditions and hooks are names a developer writes in Python; a flow cannot invent one (Q07-2). `on_pause` and `on_resume` replace what `engine/pipeline.py` does for phases 99 and 9; a flow with no step that can ask carries neither.
- `action_executor` is one composite step that runs the three `llm_per_action` steps in dependency order, as today (`AI_AGENT_PARALLEL_ACTIONS`, `AI_AGENT_MAX_ATTEMPTS`, the MCP caps).
- The result of a flow is the `Response` of `result_from` (Q09-1); the builders of `FlowResult` of the old flows move to `hooks.py` unchanged.
- The motion and expression states keep their classes (`MotionFlowState`, `ExpressionFlowState`).

## Acceptance criteria

The suite is green; **the golden file is byte-identical**; deleting `application/flows/` breaks nothing; a test adds a flow file in a temporary folder and runs it.
