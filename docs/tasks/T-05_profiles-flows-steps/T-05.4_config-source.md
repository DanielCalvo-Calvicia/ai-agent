## Goal

Everything the agent is made of (profiles, flows, step declarations, model sets, prompts) is read **once at start** through a port, so a source of the future (SQL, S3, LangChain services) changes nothing else (PR-005 section 8, Q07-17).

## Files

| Action | Path |
|---|---|
| Create | `application/outbound/ports/config_ports.py` (`ConfigSourcePort`: `load_profiles`, `load_flows`, `load_step_defs`, `load_model_sets`, `load_prompt(name)`) |
| Create | `infrastructure/outbound/config/file_source.py` (reads `profiles/`, `flows/`, `step_defs/`, `model_sets/`, `prompts/`) |
| Create | `application/engine/config_snapshot.py` (the snapshot: plain dictionaries, with `schema_version` checked) |
| Modify | `composition_root/main.py` (builds the source and the snapshot at start) |
| Create | `tests/test_config_source.py` |

## Specification

- The data is plain: no Python inside a file; a hook, a condition or a code step is a **name** the code resolves (PR-005 sections 3.3, 8).
- Every file carries `schema_version` (an integer, `1` now); an unknown version is an error that names the file. No key starts with a letter that the format does not define, except keys that start with `_` (comments, as `step_models.json` does today).
- The snapshot is read once; nothing is re-read while the service runs (Q05-14). A different source is another adapter of the port, tested with a fake in the suite.
- A file that is not valid JSON names the file and the line.

## Acceptance criteria

Reading the five folders gives one snapshot; a fake source in the tests gives the same snapshot; `application/` does not import `infrastructure/`.
