## Specification

| Profile | Steps (PR-005 section 11, Q08-3 and the review of 2026-11-02) | Tools |
|---|---|---|
| `identification` | triage | none; `default_return: "full"` |
| `chat` | draft writer, editor | none |
| `special` | triage, project manager, safety gate, action executor (worker, MCP operator, data engineer), draft writer, editor | every MCP server |
| `dynamics` | the same steps as `special` | only the Dynamics tools |
| `default` | triage, project manager, safety gate, worker, draft writer, editor (**no** MCP operator or data engineer: no tools) | none; used when a request has no profile, no token |
| `movement` | motion planner, motion validator | none |
| `gesture` | emotion reader, gesture builder | none; `inputs` `reply` and the user's message |

- Each profile uses the flow that exists today for its steps; `special` and `dynamics` get the triage as their first step. A second triage after `identification` runs and is never reported (Q09, review).
- The `models` of every profile is a model set: `proven` for `default`, `claude_mixed` for `special` and `dynamics` (the maintainer's acceptance run), `claude_haiku` for `chat`, `proven` for the others until T-06 decides. These are placeholders the maintainer may change; each is a one-line edit.
- The service no longer routes and no longer adds a gesture: a request runs the flow of its profile and returns its result.
- The ten generic profiles are the old model tables paired with the `default` flow; they live in `_unverified/` until the real-run command (T-05.17) tests each and the maintainer keeps or deletes it (Q06-9, Q07-12).
- Tokens: the maintainer chooses them; the files hold only `token_sha256`. Write placeholders (`"<hex>"`) in the repository and say so in *Notes*.

## Acceptance criteria

`assemble()` passes with these seven; each profile answers on mocks; the requests of the steps of each profile equal today's (T-05.10).
