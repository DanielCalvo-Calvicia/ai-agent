## Specification

- `detect` finds the id by the exact lines above, per table; an answer with a `job_id` it cannot read is an unknown shape, not "no job".
- `read_arguments` gives `job_id` and, only for `dynamics_v1`, `offset_rows` = `next_offset`; `state` of a read answer (`returned`, `total`, `job_id`, `offset` and the table) is `done` when it has no `pending`/`running` note, `running` when it has one, `unknown` for anything else (the interface changed in T-07.4: `state` and `merge` replace `is_done`).
- `merge` puts the table of each finished job in place of its `## <step>` section with the `pending` note, keeping the `coverage` line and the order of the answer.
- `cancel_arguments` gives `job_id`; a `not_found` answer to the cancel is not an error (the loop already ignores a cancel that fails).
- Pure functions on text; no network in these files.

Verified: 1472 passed, `check_agent.py` ok, `split_schemas.py` ok, golden untouched.
- **What each protocol reads.** `dynamics_pending`: one job per `note: pending: … as job <id> …` line; `merge` puts each result in place of its note and turns `(pending)` into `(done)` on the `coverage` line. `dynamics_v1`: `status: running` with `job_id` and `next_offset`; the result is the answer. For both, a read answer is `done` when its head has `returned`, `running` when its head says `status: running` or names a job queued, running or pending, and `unknown` otherwise. Only the head (the text above the first blank line) is read, so a customer called "Running Ltd" cannot look like a job.
- **A job whose id cannot be read** (a `pending` note or `status: running` with no id) is detected as `JobRef("")`; the engine (`follow_up`) refuses it as an unknown shape (outcome `job_unknown_shape`, `is_error`), so it is never taken as a result. One more rule of T-07.4's engine, added here.
- **Guessed, not seen:** the answer of the read tool while a job is still running was never seen (the real job was done at the first read). `status: running` and the words queued, running or pending in the head are the assumption of T-07.2's question 2; `unknown` fails visibly if it is wrong, never as an empty result. The multi-table shape (`## <step>` sections) is seen only with one table; the second is assumed alike.
- The exact lines of the shapes come from the real call of 2026-11-11 (customer `CL-1001`, scope `open`: one `pending` answer, then one job result with five rows) and from [T-01](../T-01_dynamics-mcp/T-01_dynamics-mcp.md) fact F4.
