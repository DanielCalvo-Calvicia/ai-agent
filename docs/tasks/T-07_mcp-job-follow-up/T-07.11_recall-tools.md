## Goal

The three shipment tools are **composed** answers: when one of their inner queries is a job, the service answers `status: running` with that query's `job_id`, and reading that job gives the rows of the inner query, not the shipment table (the answer of T-07.2, question 5). Reading it would hand the writer wrong data. These tools must be called again after `retry_after_seconds`, never read.

## Specification

- `job_recall_tools` is an optional list in a server file, meaningful with a `job_protocol` other than `none`. A name outside `allowed_tools` or a value that is not a list of names skips the server with a warning.
- For a call to one of those tools whose answer holds a job (any protocol), the loop waits 3 s (the service's `retry_after_seconds`, cut to what is left of the 60 s), then calls **the same tool with the same arguments**; the answer of that call is read as any other (`done`, `running` again, or not understood). The time is spent as for a read; when it ends, the job named by the first answer is cancelled with the cancel tool and the answer says it is still running.
- Nothing the model or an answer says picks the tool: it is the tool the step was running, with its own arguments. The read tool is not called for these tools.

## Acceptance criteria

A shipment call that answers `running` once and then the table gives the table (one call record `job_done`, the tool called twice, its job never read, 3 s of wait); one that keeps running is called again until the time is spent and then cancelled; a tool that is not in the list still has its job read; the settings are checked; the suite passes with the golden file untouched.
