## Goal

Learn from the maintainers of `dynamics_microservice` what shape its job answers really have, and, if they agree, ask for a single explicit one. It does not block T-07.3 to T-07.8: the agent is built for the shape seen on 2026-11-11 and for the older one.

## What to do

1. Send the prompt below to the session of `dynamics_microservice` (the project is read-only for this plan: it is never edited from here).
2. Record the answers in *Notes*: the shape of `ok`, `running`, a finished job, a job not found and a `scope` all answer with one job running; `MCP_JOB_WAIT`; the life of a job; whether `cancel_job` works on a job a workflow started; whether the shipment tools are final.
3. Put a real example of each kind (placeholders for customer and order data) in `tests/fixtures/`, as T-07.7 says.
4. If the service changes its shape, note the date, and set the protocol of its file to the new one in a later task (`dynamics_v1` or a new name).

## Prompt to send

```text
Context: ai-agent (Python, the "mind" of OBLIVION) reads Business Central through the MCP tools of this service (Streamable HTTP). A real call on 2026-11-11 showed that the shape of a "job" answer differs from what ai-agent's documents and tests assume. ai-agent is going to follow jobs in code, with one protocol per server (ADR-018, proposed). I need you to confirm what this service does today and, if you agree, make the job answers consistent. Change nothing until you have answered part 1.

PART 1 - Confirm (read the code and docs of this service; no changes)
1. What does a workflow tool answer when its query is not done after MCP_JOB_WAIT? For customer_orders (customer_no=CL-1001, scope=open) I saw:
   coverage: ...; steps: open_orders (pending); customer_no=CL-1001
   ## open_orders (open)
   note: pending: the query is still running as job <id> (running): read it with get_job_result
   There was no `status: running` line and no `next_offset`. Your docs describe `status: running` with `job_id` and `next_offset`. Which is the real, intended contract? Is `pending` a change in this service?
2. get_job_result answered with `returned`, `total`, `job_id`, `offset: 0` and the table. When a job is finished, is there ever a `next_offset`? How does a client know a result is complete, and how does it read page 2?
3. With scope=all (two tables) can each step have its own job? What does the answer look like when one table is done and the other pending?
4. What are MCP_JOB_WAIT, the job lifetime and what does an expired job answer? Does cancel_job work on a job a workflow started?
5. The tool list now has order_shipments, shipment_status and shipment_tracking, and the customer_no pattern accepts "_". Are these final?

PART 2 - Proposed change (only if you agree)
Every answer that can carry a job uses the same machine lines at the top:
   status: ok | running | error
   job_id: <id>                  (only when running)
   retry_after_seconds: <n>      (only when running)
   next_offset: <n>              (only when more rows can be read)
with the same format for each table of a multi-table answer (a per-table status). get_job_result answers with the same header and says explicitly when the result is complete. Keep MCP_JOB_WAIT below 30 s (ai-agent's call timeout is 30 s and a message may wait 60 s for its tools). Never answer `pending` without a job_id.

Constraints: ai-agent accepts the shape each server has today, so this is not a blocker. If the shape changes, tell me the date and keep the old lines for a while. Read-only stays. No customer data or tool arguments in logs. Add a contract test with a snapshot of each kind of answer (ok, running with a job, finished job, job not found, two tables with one job) and tell me where it is.

Answer with: (a) part 1, (b) what you changed or will change, (c) one real example of each answer kind.
```

## Acceptance criteria

The five questions are answered in *Notes*; a real example of each answer kind is in hand (placeholders only); the maintainer knows whether the shape of 2026-11-11 is final.
