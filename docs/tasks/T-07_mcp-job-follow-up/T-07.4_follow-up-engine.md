## Specification

- **Reads:** until the job is done or the budget of the message (`tool_wait_budget`, 60 s in total) has nothing left; each read uses the time that is left, as any call does. The wait between two reads is a constant at the top of the file (T-07.1 question 3).
- **One job per table, all or nothing (Q10-9):** every job of an answer is followed; the answer given back keeps its tables only when **all** jobs ended. If one does not end in time, the ones still running are cancelled and no table is given, not even one that ended.
- **Budget spent:** call `cancel` if the server file names a cancel tool; give back a plain "still running" answer that the writer can say; never an empty result.
- **Unknown shape** (the protocol cannot read the answer of a read): the action fails with a reason; one log line with the server name and the outcome.
- Offsets: `offset_rows` goes only when the protocol gave one.
- No tool argument or answer in a log line, metric or span.

## Acceptance criteria

With a scripted protocol: a job that ends on the second read gives the final answer; a job that never ends spends the budget, is cancelled and gives "still running"; two jobs in one answer that both end give both tables, and if one never ends none is given and the other is cancelled; an unknown shape fails with a reason; the log lines hold no value.

- **Not done, on purpose:** reading a second page of a result (`next_offset`): a result is the first page, as today; the protocols of T-07.5 decide whether a page with `next_offset` is a result. The `attempts` of a followed call counts the call and its reads.
