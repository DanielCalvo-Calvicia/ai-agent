## Specification

- Variable `AI_AGENT_MAX_MCP_CALLS_PER_MESSAGE`: a whole number; **`0` means no limit**; default **5**.
- A value that is not a whole number or is negative falls back to **5** with a warning (never to `0`, so a typing mistake does not remove the limit).
- The cap counts MCP actions **run** in one message (retries of the same action do not count).
- When the cap is reached the remaining MCP actions are **not run**: they are marked failed with a reason that says the limit was reached, so their dependants are skipped as for any failed action. The final writer and editor are told (through the actions' errors, the way a failed action already reaches the writer) so the **reply says plainly that only the first N could be done** (a personalised message, written by the last step of the flow: Q04-3).

## Acceptance criteria

With the cap at 2 and a plan of 4 MCP actions, 2 run, 2 are skipped, and the reply says it could only do 2; with `0` all 4 run; an invalid value uses 5 with a warning.

## Notes

- **2026-10-27, built.** `failure.py`: `max_mcp_calls()` (default 5, `0` = no limit; empty is the default silently; not a whole number, `2.5`, `1e3` and negative fall back to 5 with a warning, never to 0). `action_executor.py`: `run()` reads the cap once per run (so the warning is not repeated per action) and zeroes the count; `_run_mcp` counts an action when it **starts**, after the confirmation check, so a retry of the same action, a blocked action and an action skipped because a dependency failed are not counted. Over the cap it returns the error `MCP_CAP_REACHED` ("The step was not run: the limit of N tool calls for one message was reached, so only the first N could be done."), which marks the action failed: its dependants are skipped by the existing rule, and the later steps receive it with the other actions. MCP actions run one by one, so the count needs no lock. `.env.example`, the environment-variables and architecture documents are updated.
