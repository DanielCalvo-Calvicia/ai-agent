## Goal

A tool call is not cut while the server is still waiting for its query, and it is not retried when a retry cannot help. The Go service waits up to 20 s (F4) and the current limit is 10 s for the whole session (F7).

## Specification

- Two limits: listing tools stays short (10 s); executing a tool uses a configurable limit from `AI_AGENT_MCP_CALL_TIMEOUT_SECONDS`, default **30**, always larger than the Go `MCP_JOB_WAIT`. An invalid value (not a positive number) falls back to the default with a warning.
- The limit covers connect, initialize and the call, as today.
- A timeout gives the existing `{"error": ..., "is_error": True}` answer; the message must say it was a timeout, so the planner can tell it from a tool error.
- **Retries (Q03-4 A).** Retry **only** a transport error (the server could not be reached or the connection broke) and `error (retry_later)`, **once**. **Never** retry a timeout, `error (input)`, `error (not_found)`, `error (source_problem)` or `error (internal)`. The rule is for MCP tool calls; the retries of an LLM call and of a step that answers `retry` stay as they are (`AI_AGENT_MAX_ATTEMPTS`).
- The total wait of a message that follows up a running query is 60 s (Q01-10); T-01.6 enforces it. This task only provides the call limit.

## Acceptance criteria

A transport error and `retry_later` are retried once and no other failure is retried, and a step whose tool failed for good is not asked again by the step loop; a server that answers after 15 s succeeds; one that never answers fails at the call limit with a timeout message; listing a dead server still gives up at 10 s.

## Notes

- **2026-10-27, built.** `tool_catalog.py`: `SERVER_TIMEOUT_SECONDS` became `LIST_TIMEOUT_SECONDS = 10` (listing only) and `call_timeout_seconds()` reads `AI_AGENT_MCP_CALL_TIMEOUT_SECONDS` (default 30; zero, negative, non-numeric, `nan` and `inf` fall back to 30 with a warning). `tool_executor.py`: the call uses that limit; a timeout answers `MCP call timed out after N seconds.`; a transport error answers a fixed sentence (the raw text can hold the address, so it is not returned); a tool error now returns its text (it used to return the raw content list); a `ValueError` from the config (no url, unsupported type) is a configuration error and is not retried. **One retry**, only after a transport error or `error (retry_later)` (the kind is searched in the text, so it also works behind FastMCP's "Error executing tool" prefix); logged with the tool name and the reason only.
- Timeouts inside the exception groups the MCP clients raise are recognised (`_is_timeout` walks them), and `httpx.TimeoutException` counts as a timeout.
- Tests (28 in the two integration files, plus the config ones): the default 30 and the listing 10, invalid values, a slow answer inside the limit, a call that never answers (timeout message, one run on the server), `retry_later` once and twice, a tool error that is not retried, a transport error retried once with the address not in the answer. **The 15 s case of the acceptance criterion is proven with a shorter wait (1.5 s with a 5 s limit)** to keep the suite fast; the limit being configurable and above the old fixed 10 s is covered by the default test.
- **Step retry loop: decided 2026-10-27 (build it).** The loop of `action_executor.py` (`for attempt in range(max_attempts())`) re-asks the whole phase-5 LLM step when it produced no output, and the tool runs inside that step, so a timeout or a non-retryable tool error could be called again. Built: `application/outbound/ports/mcp_ports.py` has `watch_tool_failures()` (a context manager that holds a `ToolFailures` for one attempt, in a context variable) and `report_final_tool_failure()`; `MCPToolExecutor.execute` calls the latter whenever the answer is an error (its own retry, if it deserved one, is already spent; a tool nobody offers also counts); the loop wraps each attempt in the former and, when the attempt produced no output and a failure was reported, stops asking (warning with the action id and the attempt, never a value). A step that produced nothing for another reason is still asked again up to `AI_AGENT_MAX_ATTEMPTS`; a step whose later tool call succeeded has output and is not affected. This works because the loop, `ai_sdk` and the handler share one thread and context (MCP actions run one by one, and only non-MCP actions go to the thread pool); if a caller ever ran the handler in a thread without the context, nothing is reported and the loop behaves as before. **Not changed on purpose:** the retries of an LLM call (`phase_runner.py`) and of a step that answers `retry` (`pipeline.py`); they can still re-run a step that had a tool in it.
- Files added to the task by this decision: `application/outbound/ports/mcp_ports.py`, and the new test `tests/test_mcp_step_retry.py` (a scripted step that never answers: asked 3 times without a reported failure, once with one; outside a watched step nothing happens). `tests/test_mcp_streamable_http_integration.py` also checks that the executor reports `not_found`, an exhausted `retry_later`, an unknown tool and a timeout, and does not report a success, even after a retry.
