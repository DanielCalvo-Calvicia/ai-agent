## Specification

- Per call: the **tool name**, the **outcome kind** (`ok`, `timeout`, `input`, `not_found`, `retry_later`, `source_problem`, `internal`, `transport`) and the **duration**. **Never** the arguments or the answer (Q02-7).
- The outcome kind of a tool error is read from the text `error (<kind>): ...` that the Go service sends; anything else is `internal`.
- A log line per call (the tool, the outcome, the duration).
- `SessionMetrics` keeps the list of tool calls of the message next to the tokens.
- Langfuse (when its keys are set): a span per tool call named after the tool, with the outcome and the duration as metadata and no input or output. A failure of the reporter never breaks a call.

## Acceptance criteria

A scripted call records one entry with the right kind and a duration; no log line, metric or span holds an argument or an answer; the reporter failing does not break the call.

## Notes

- **2026-10-27, built.** The executor lives in `infrastructure/` and the metrics belong to a message, so the call travels through the same per-attempt channel T-01.4 made for failures: `mcp_ports.py` has `ToolCallRecord` (tool, outcome, `duration_ms`, `attempts`, wall-clock start and end) and `report_tool_call()`; `ToolFailures` also collects `calls`; `MCPToolExecutor.execute` measures the whole call (its retry included), classifies it and reports it, and writes the log line `MCP tool call`; the action loop, in a `finally` so a failing step loses nothing, hands the collected calls to `SessionMetrics.record_tool_call`, which keeps them in `tool_calls` (also in `summary()` as `tool_calls`) and passes them to the reporter inside `try/except`.
- **Outcome kinds.** `ok`, `timeout`, `transport`, `not_found` (also when no server offers the tool, with 0 tries) and the kinds a tool may say (`input`, `not_found`, `retry_later`, `source_problem`, `internal`, read from `error (<kind>): ...`). Anything else is `internal`, including a text with no kind, an unknown kind, and a tool that says `error (ok)`, `error (timeout)` or `error (transport)`: those three names are ours, not the tool's. A configuration error (no url, unsupported type) is `internal`. A call that was retried reports its **final** outcome with `attempts: 2`.
- **Langfuse.** `LangfuseUsageReporter.report_tool_call` queues a span named after the tool, child of the message's root span, with `outcome`, `duration_ms`, `attempts` and `kind: mcp_tool_call` as metadata, no input or output, level `ERROR` when the outcome is not `ok`. The tool span is reported while the step runs and its generation after it, so either can be the first to find the message without a root span: the creation of the root moved into one helper (`_root_span_if_new`) that both use (the existing events are unchanged, their tests pass). The usage port method is **not abstract**: a reporter that does not know it ignores tool calls.
- **Golden file regenerated on purpose** (`UPDATE_GOLDEN=1`): the only diff is the 14 lines `"tool_calls": []`, one per scenario (no scenario runs a real tool).
- **Limit, by design:** a tool call is only counted in `SessionMetrics` when it happens inside an MCP step of the special flow (the only place tools are used today); anywhere else it is logged and not counted.
- Tests: the kind of every way a call can end, with the real client (ok, `not_found`, `retry_later` exhausted and recovered, an unknown tool, a timeout, a transport error) and with a fake (every kind a tool can say, plus the ones it must not); the log line holds exactly `tool_name`, `outcome`, `duration_ms`, `attempts` and no value; the metrics keep the calls next to the tokens and are not counted as LLM requests; the reporter failing, missing or old does not break the call; the Langfuse span has no input or output; the root span is created once whichever comes first; a scripted step hands its calls to the metrics through the action loop.
